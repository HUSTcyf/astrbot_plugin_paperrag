# [2.1.0] - 2026-05-13

## 评估系统重构、知识提取流水线、Token 预算管理与 Wiki 引擎

本次更新重构了 Ragas 评估管线（答案生成与指标评分 LLM 分离），新增了 RAG 问答后自动知识提取到 Wiki 的流水线，实现了 token 精确预算管理防止上下文溢出，修复了本地 VLM 生成 Cypher 的语法幻觉问题，并引入了 LLM Wiki 存储引擎。

---

### Token 预算管理：精确控制 RAG Answer Prompt 上下文

**核心变更**：`_build_rag_answer_prompt()` 使用 `count_tokens()`（cl100k_base 编码器）进行精确 token 计数，以 `llama_vlm_n_ctx` 作为上下文窗口，为 chunks 动态分配 token 预算。超出预算时优雅截断，第一个 chunk 超出限制时抛出明确错误。

| 文件 | 变更 |
|------|------|
| `commands/retrieval_helpers.py` | `_build_rag_answer_prompt()` 重写：提取 `_PROMPT_TEMPLATE` 常量；用 `count_tokens()` 计算固定开销（prompt 模板 + query）；扣除 `text_llm_max_tokens` 输出预留后，剩余 tokens 按序装入 chunks（每个 chunk 精确计数文本+分隔符）；溢出时 `logger.info()` 记录截断信息；无 `llama_vlm_n_ctx` 配置时保持向后兼容全量装入 |
| `rag/token_utils.py` | 新增 `truncate_text_to_tokens()` 公共函数：使用 cl100k_base 编码器精确截断文本到指定 token 数 |

**Token 预算公式**：
```
available = llama_vlm_n_ctx - text_llm_max_tokens - base_tokens
```
其中 `base_tokens` 为 prompt 模板格式化的固定文本 token 数（不含 chunks）。

### 知识提取流水线：自动提取 RAG 问答事实到 Wiki

**核心变更**：每次 RAG Q&A 完成后，自动将可验证事实提取为结构化 Wiki 页面（实体/概念/对比），经过两轮 LLM 独立校验（extract → critique → filter → write_to_wiki），仅高/中置信度页面写入。

| 文件 | 变更 |
|------|------|
| `agentic_rag/knowledge_extractor.py` | **新增（265 行）** — `run_knowledge_extraction()` 主入口，内联 extract → critique → filter → write 四步流水线；两轮独立 LLM 调用：提取（temperature=0.2）和批判验证（temperature=0.1，五维核查：来源支撑、准确性、过度泛化、完整性、一致性）；仅保留 KEEP 且非 low 置信度页面；`_parse_json()` 使用 Unicode 转义处理中文引号；`_format_sources_for_prompt()` 使用 `count_tokens()` + `truncate_text_to_tokens()` 精确截断源文本；`_log_context_overflow()` 在 prompt 接近 `llama_vlm_n_ctx` 时告警 |
| `agentic_rag/__init__.py` | 导出 `run_knowledge_extraction` |
| `commands/paper.py` | `_search_command()` 中新增 fire-and-forget hook：配置 `auto_extract_knowledge=true` 时，通过 `asyncio.create_task()` 非阻塞调用 `_extract_knowledge_to_wiki()`；失败不影响主流程（`logger.warning()` 记录）；`import asyncio` 移至文件顶部 |

### 评估系统：Answer Generation 与 Metrics LLM 分离

**核心变更**：Ragas 评估中，答案生成必须使用系统自身的 VLM（`provider.llm_utils.call_llm()`），而 Ragas 指标评分使用云端 LLM（`--eval-llm-*`）。此前两者混用同一个云端模型，无法评测系统自身的检索+生成能力。

| 文件 | 变更 |
|------|------|
| `evaluation/ragas_evaluator.py` | `RAGQueryWrapper` 新增 `context`/`config` 参数；`_generate_answer()` 优先调用 `call_llm()`（VLM），失败时 fallback 到云端 LLM（2 次重试）→ context text → 空字符串；修复 gate condition 阻塞系统 LLM 路径；修复返回 `None` 的边界情况；删除 llama-index 分支死代码（~30 行）；删除 `demo main()` 和 `if __name__` 块 |
| `evaluation/run_evaluation_ragas.py` | 抽取 `_build_rag_config()` 消除重复 RAGConfig 构造（~45 行）；`run_evaluation()` 透传 `context`/`config`；删除 `_MinimalLLMProvider` 死类（~12 行）；删除 `MULTIMODAL_QUESTION_PROMPT` 孤儿常量（~25 行）；修复 `embed_base_url` 不对称 |
| `provider/llm_utils.py` | 补充缺失的 `from astrbot.api import logger` 模块级导入（`get_llm_provider()` 中使用 `logger.debug()` 但未导入） |

### Cypher 生成：修复本地 VLM 语法幻觉

**问题**：Qwen3.5-9B VLM 生成 Cypher 时出现两类语法错误，导致知识图谱召回通道静默跳过：

1. `{{name: 'SfM'}}` — 过度转义大括号（应为 `{name: 'SfM'}`）
2. `(t:Baseline {name: 'A'}|{name: 'B'})` — 将关系类型合法的 `|` 语法错误应用到节点属性模式

**修复**：

| 文件 | 变更 |
|------|------|
| `graphrag/graph_rag_engine.py` | `_TEXT_TO_CYPHER_TEMPLATE` 新增显式反例（`|` 在节点模式中非法、多值匹配用 `WHERE IN`）；新增 `_sanitize_pipe_in_node_properties()` 正则修复函数；`_validate()` 增加三层预处理：`{{}}`→`{}`、pipe sanitizer、`}})`→`})` |

Cypher 校验器（`_make_cypher_validator`）此前已有，但只能**检测**错误并抛异常，导致图谱通道静默返回空。新增的 sanitizer 是**修复器**，在进入 `EXPLAIN` 校验前纠正已知的 LLM 错误模式。
